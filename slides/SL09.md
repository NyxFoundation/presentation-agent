Speaker Notes:

【概要】
S1-B は「暗号で守る」だけでは不十分という話。安全装置が "発火した事実" を後から検証可能に出力できないと、紛争時に何も主張できない。Proof-of-Exploit は社会実装版のフェイルストップ機構で、AI が見つけた脆弱性の存在を ZK 証明として on-chain に出し、コントラクトが自動停止する仕組み。

【重要な前提】
福島第一原発の教訓 — 安全装置が "作動した証拠 / 作動しなかった証拠" を独立に検証する手段がなかった。同じ問題はあらゆるデジタル機構で起きる。Proof-of-Exploit は「安全装置の発火 = ZK 証明の検証成功」と等価にすることで、紛争時に物理的に検証できる証拠を残す。なお Proof-of-Exploit は 2024-25 年に 0xPARC / EF research を中心に議論されている設計パターンで、production deployment はまだ限定的。

【概念図の読み方 (静的アーキ図、一目で全体像がわかる構成)】
上部の amber バナーは「今、監査ループの中で何が起きているか」を示すコード風キャプション: `audit_loop: scan(C) // exploit 発見、まだ drain していない`。
- 左上 OFF-CHAIN (継続監査、indigo 枠): AI Auditor (虫眼鏡アイコン) が witness W を発見 → 矢印で ZK Prover (π アイコン) に渡り、`π = Prove(∃W : drain(W,C))` を生成。
- 中央のオレンジ矢印 (「π を on-chain に submit」ラベル付き): OFF-CHAIN で作った π が ON-CHAIN 側に提出される、この図の主動線。
- 下部 ON-CHAIN (プロトコル+暗号的ガード、green 枠): ZK Verifier (shield ✓ アイコン) が π を受理 → Circuit-Breaker (電源アイコン) が発火 → DeFi Contract (南京錠アイコン) が halted、drain 阻止。
- 右側の 2 つの白カード: 「W (witness) は秘密のまま on-chain には π だけを提出」「π は ON-CHAIN に永続 (紛争時の証拠)」という 2 つの性質を補足。
- 中央右の破線カード「KelpDAO の場合 (具体例)」(LayerZero / KelpDAO ロゴ付き): p4 で見た抽象的な W と DeFi Contract を、KelpDAO の実例に当てはめると何になるかを示す差分。W = 「config の requiredDVNCount が 1」、DeFi Contract = 「rsETH Bridge (release() を阻止)」。p4 は「侵害された瞬間 (実際に起きたこと)」だけを描いた図だったので、この差分カードが「この仕組みを足していたら何を証明し、何を止めていたか」を p6 側で補完する。

全体を通して、drain は一度も起きていない (exploit の存在が π という形で暗号的に確定した時点で contract 側が自動的に止まる、という一枚の絵)。

【講義での強調点】
- "暗号で守る" だけでなく "守れた事実" "破られた事実" を検証可能にすることが重要。これが福島の教訓を社会実装版に変換した姿。
- 従来の検知系との対比 (発話だけで触れる):
  • 正しさの保証: 運営の主張 → 数学的 ZK proof
  • 機密性: exploit 公開 → witness は秘匿のまま π だけ on-chain
  • 自動化: 人手介在 → contract が自動 pause
  • 紛争時の証拠: 改ざん可能なログ → 暗号的に拘束された on-chain proof
- 本図では drain が起きていない。これは ZK proof が exploit より先に on-chain に届いたシナリオ。実際の deployment では proof 生成時間との競争が課題で、これは S3-B 罠 #4 "witness generation がボトルネック" の伏線。
- 「W は秘密のまま」がポイント: ZK 性により Verifier には exploit の内容を見せず "存在することだけ" を伝える。同じ手法で responsible disclosure を強制可能。
- KelpDAO 例との接続: Proof-of-Exploit は「攻撃の事実を on-chain で発火させる」モデル。S1-A の "攻撃側のスコープに守備が追いつかない" 問題に対して、暗号で "発火した事実" 自体を作る側に回す発想。図中の「KelpDAO の場合」カードが示す通り、DVN の署名が本物か偽物かを検証する必要すらない (RPC の嘘を見抜かなくても、config が 1-of-1 であること自体を証明できれば halt できる) 点が ZK light client 案 (source chain 状態を直接検証) との違い。
- ホワイトボードへの伏線: 午後 KelpDAO のホワイトボードで「ZK light client / Proof-of-Exploit、どちらが現実的に防げたか?」と同じ系譜の議論を行う。
