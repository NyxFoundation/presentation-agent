Speaker Notes:

【概要】
S1-B は「暗号で守る」だけでは不十分という話。安全装置が "発火した事実" を後から検証可能に出力できないと、紛争時に何も主張できない。Proof-of-Exploit は社会実装版のフェイルストップ機構で、AI が見つけた脆弱性の存在を ZK 証明として on-chain に出し、コントラクトが自動停止する仕組み。

【重要な前提】
福島第一原発の教訓 — 安全装置が "作動した証拠 / 作動しなかった証拠" を独立に検証する手段がなかった。同じ問題はあらゆるデジタル機構で起きる。Proof-of-Exploit は「安全装置の発火 = ZK 証明の検証成功」と等価にすることで、紛争時に暗号的に検証できる証拠を残す。なお Proof-of-Exploit は 2024-25 年に 0xPARC / EF research を中心に議論されている設計パターンで、production deployment はまだ限定的。

【概念図の読み方 (静的アーキ図。前ページ p4 の KelpDAO 図との「差分」として描いている。生成スクリプト: figures/poe_arch.py)】
基底部は p4 とまったく同じ: User → Karak L2 Contract → LayerZero バンド内の DVN #1 (amber, 1-of-1)、ゴーストの DVN #2/#3、下段の Karak RPC 5 台 (2 台改ざん・3 台オフライン)、上部の setConfig(requiredDVNCount: 1) callout。攻撃は p4 と同じように進行している (偽の応答 → DVN #1 が署名 → release() 要求)。

- 右上 off-chain: AI Auditor (虫めがね) が config を継続監査し、p4 で事故原因だった赤い「1」そのものを exploit witness W として発見。W を ZK Prover (π) に渡し、π = Prove(∃W : exploit) を生成して on-chain へ submit (直角の緑破線が ZK Verifier の上辺に着地)。

【講義での強調点】
- p4 との差分は 4 つだけ: AI Auditor / ZK Prover (off-chain) + ZK Verifier / Circuit-Breaker (on-chain)。コントラクト本体にも DVN にも手を入れていない。
- 「W は秘密のまま」がポイント: ZK 性により on-chain には π だけが載り、exploit の中身 (どう攻撃するか) は公開されない。responsible disclosure を暗号で強制できる。
- 攻撃が来てから止めるのではなく、「exploit が存在する」という事実の証明が先に on-chain に届けば drain 自体が起きない。実運用では proof 生成時間との競争が課題 — S3-B 罠 #4 "witness generation がボトルネック" の伏線。
- π は on-chain に永続するので、紛争時 (LayerZero と Kelp の責任論争のような場面) に「安全装置が正しく発火した」ことを第三者が検証できる。これが福島の教訓の社会実装版。
