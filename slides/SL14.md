# S2-A. ZK / MPC / FHE — <strong>敵対モデル</strong>で整理する

<table class="text-xs mt-2">
<thead>
<tr><th></th><th class="bg-amber-50">ZK</th><th class="bg-green-50">MPC</th><th class="bg-blue-50">FHE</th></tr>
</thead>
<tbody>
<tr>
<td><strong>隠す対象</strong></td>
<td>prover の証言 (witness)</td>
<td>各参加者の入力</td>
<td>計算データと中間状態</td>
</tr>
<tr>
<td><strong>信頼前提</strong></td>
<td>prover を信頼しない<br/>verifier も信頼しない (ZK 性)</td>
<td>k-of-n を信頼</td>
<td>server に<strong>データ機密</strong>は信頼しない<br/>(計算正しさは別途必要)</td>
</tr>
<tr>
<td><strong>敵対モデル</strong></td>
<td>malicious prover (soundness) <br/>+ malicious verifier (ZK)</td>
<td>up to t corrupt parties<br/>(semi-honest / malicious)</td>
<td><strong>素の FHE</strong>: semi-honest server<br/>malicious server には<strong>追加で ZK</strong>が必要</td>
</tr>
<tr>
<td><strong>計算正しさ保証</strong></td>
<td>proof で保証</td>
<td>多数決 / cryptographic check</td>
<td><strong>素の FHE には無い</strong> → Verifiable FHE で補う</td>
</tr>
<tr>
<td><strong>主な用途</strong></td>
<td>計算の正しさ証明</td>
<td>共同計算</td>
<td>計算の委託 (機密のみ)</td>
</tr>
</tbody>
</table>

🧭 <strong>判断のコツ</strong>:
- "<strong>1人</strong>の正しさを<strong>他者</strong>に納得させる" → ZK
- "<strong>複数人</strong>でデータを<strong>合算</strong>したい" → MPC
- "<strong>計算を委託</strong>したい (データは渡したくない)" → FHE

ZK・MPC・FHE を機能で並べるのではなく、敵対モデルで整理した表です。隠す対象の行は、それぞれが「何の秘密性を守るのか」。ZK は prover の証言、MPC は各参加者の入力、FHE は計算データと中間状態。信頼前提の行が一番重要です。ZK は prover も verifier も信頼しない、MPC は k-of-n を信頼。FHE で注意してほしいのは、素の FHE が保証するのは「データの機密性」だけで、計算の正しさは保証しないという点です。malicious な server は復号後に検出できない不正な計算を返せます。だから「server を信頼しない」と一言で書いてはいけません。Verifiable FHE は ZK を後付けで合成して計算正しさを補う方向です。敵対モデルの行で、ZK は soundness の文脈では malicious prover を、zero-knowledge の文脈では malicious verifier を考えるという二重性があります。これは S3-B 罠 #2 で扱う「soundness ≠ ZK」の伏線です。判断のコツとして、1人の証言を他者に納得させたいなら ZK。複数人でデータを合算したいなら MPC。計算を委託したいなら FHE。Open Question です。30秒。結婚マッチングを ZK・MPC・FHE で作るならどう違うか。S3-A の板書実演でも使う例です。
