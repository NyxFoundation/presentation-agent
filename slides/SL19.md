Speaker Notes:
【概要】Jolt は Arun-Setty-Thaler (2024) の汎用 zkVM。設計思想を一文で言うと「CPU の各 step を、巨大 lookup table T の数エントリ参照に分解する」。

【図の読み方】左 = RISC-V program、中央 = execution trace (t1, t2, ... の連なり)、下 = 全 RISC-V 命令を埋め込んだ lookup table T、右 = Lasso (lookup argument) と Sumcheck (基盤プロトコル)。各 step は T のあるエントリを「参照する」だけと解釈できる。

【各 phase の物語】
phase 0 — RISC-V program。Rust や C で書いた任意プログラムをコンパイルしたもの。
phase 1 — execute → trace。CPU の各 cycle が step box として並ぶ (t1, t2, t3, ...)。
phase 2 — 各 step ←→ T のエントリ。すべての RISC-V 命令が T 内に格納済 (|T| ≈ 2³² entries)。
phase 3 — Lasso (Setty et al. 2023): ある値 x が T に属することを |T| に依存しない時間 (∝ log|T|) で証明する lookup argument。trace 全体の lookup を 1 つに束ねる。
phase 4 — Sumcheck (前スライド): Lasso bundle を Fiat-Shamir 経由で SNARK 化、verifier に確信させる。
phase 5 — ✓ zkVM proof。Groth16/PLONK 比で 2x 高速 prover。プログラム書き直し不要。⚠ ただし T の precompute メモリ要求が大きい → mobile/IoT には不向き (罠 #1)。

【講義での強調点】
- 「制約系を書き換えない」は単に開発体験ではなく経済性に直結。書き換えコストが消えると、プログラム言語の選択肢が広がる
- Lasso が「lookup の革命」と呼ばれるのは |T| 独立の証明時間
- precompute memory は実運用の桁違いの差として効く — S3-B 罠 #1 でカードを配る
- SP1 (Succinct) や RISC0 もこの zkVM 路線。Jolt は a16z バックの代表例
- 次スライドで「コミットメント + folding」を補強要素として見る
