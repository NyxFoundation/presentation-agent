Speaker Notes:
【概要】Longfellow は Google が 2025/7 に OSS 化、Programmable Cryptography の社会実装の象徴。設計思想を一文で言うと「世界中で既に発行されている mDOC / JWT / W3C VC を、そのまま ZK 化する」。

【図の読み方】3 actor 横並び — Issuer (運転局/銀行/大学) → User wallet (Google Wallet / EUDI) → Verifier (EC サイト/銀行)。上部の灰色 dashed band が「EXISTING ID STANDARDS — no change」を示す。Longfellow は既存標準を壊さず上に乗る。

【各 phase の物語】
phase 0 — Issuer が既存通りの方式 (ECDSA + SHA-256) で mDOC / JWT を発行・署名。何も新しい暗号は要求しない。
phase 1 — User wallet が VC を受領・保管 (Google Wallet, EUDI Wallet 等)。
phase 2 — Verifier が predicate を問う: 「age ≥ 18 ?」。原本 ID は要求しない。
phase 3 — User wallet が π を生成: ZK { ∃ VC : Sig(VC) ✓ ∧ age(VC) ≥ 18 }。技術は MPC-in-the-head (Ligero 系) + Σ-protocol で既存署名を ZK 化。Sumcheck / Jolt とは別系統。
phase 4 — Verifier が π を受領・verify。"≥18 ✓" の事実だけ取得、生年月日・氏名・原本 ID は一切漏れない。
phase 5 — Deployment status: Google Wallet deploy 済 ｜ Bumble 認証稼働 ｜ EUDI Wallet 候補 ｜ IETF CFRG 標準化議論 ｜ Trail of Bits + Ligero 監査済 (2025)。

【講義での強調点】
- 「既存標準を壊さない」が社会実装の鍵 — 新しい暗号を採用する political/operational コストはゼロ
- Sumcheck/Jolt とは別系統 (MPC-in-the-head 系の Ligero) — 系譜を混同しない (S2-C 序論の主題)
- Open Question への回収: Longfellow は分類学的に「Σ-protocol + MPC-in-the-head 系の非対話 ZK」、既存 zkSNARK では合成性と既存 signature への適合性が足りなかった
- EU 年齢確認義務 (2025/7) → Google が Longfellow を Sparkasse 提携で公開、社会実装の象徴的事例
- 次スライド S2-C ⑤ で ZK Bridge / Light Client へ — Longfellow と同様に「既存 chain 状態を ZK 化」のパターン
- S2-D で同じ仕組みを Google Wallet スマホ画面でライブデモ
