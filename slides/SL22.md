Speaker Notes:
【概要】ZK Bridge (a.k.a. ZK light client) は、cross-chain メッセージング層を「RPC ノードの信頼」ではなく「暗号的な state proof」で繋ぐ設計。午後のホワイトボードで議論する KelpDAO × LayerZero $292M 事件と直結する S2 最後のトピック。

【図の読み方】左 = source chain、右 = destination chain、下中央 = off-chain prover。phase が進むにつれて user event → state read → proof gen → on-chain verify → release と一方向に flow。RPC ノードは図中に登場しない (信頼しないので存在意義がない)。

【各 phase の物語】
phase 0 — idle: 2 つの chain と prover。light client コントラクトは destination に事前 deploy 済。
phase 1 — User が source.block_N で rsETH を burn (Kelp と同じトリガ)。
phase 2 — Prover が source.state @ block_N を読み取る — state root と merkle proof から暗号的に取得。RPC ノードの応答は使わない (内容を暗号的に検証可能なため)。
phase 3 — Prover が π = ZK { source.state @ block_N ∧ burn(amount) ⊆ state } を生成。証明系は Sumcheck 系 (Polyhedra) や zkVM (Succinct SP1) のどちらか。
phase 4 — π を destination の light client にポスト → on-chain で verify(π) → 暗号的に成立。RPC が嘘でも proof は通らない。
phase 5 — release(user, amount) が走る。⚠ ただし「source chain の RPC が同じく侵害されたら?」は午後の講師突っ込み弾 — full node 自体が嘘の state を出せばどうなるか、議論の種。

【講義での強調点】
- 「RPC を信頼するな」は新概念ではないが、ZK light client は具体的解の 1 つ
- 代表実装: Polyhedra zkBridge (Sumcheck 系、汎用 multi-chain) vs Succinct Telepathy (SP1 zkVM、Ethereum 中心)
- トレードオフ: 汎用性 vs 最適化、proof size vs prover cost
- ホワイトボード議題: 「Kelp が ZK light client だったら防げたか?」「source RPC が侵害されたら?」「gas コストは現実的か?」
- 4 つの設計方向のうち「ZK 路線」のシード — グループはここから出発するか、別路線 (threshold MPC, 複合, 暗号で防げない派) を選ぶか決める
- S2 終了 → S2-D の Longfellow ライブデモで触感を付けてから休憩へ
