Speaker Notes:

【概要】
4 つの問い (①何を守る? ②誰が計算? ③いつ? ④誰が検証?) を 2 つの具体サービス (SMBC 日興 DeFi API privacy / 結婚マッチング) に同時適用する板書実演。同じテンプレートから ZK と MPC、別々の最適解が導かれることを 1 枚で示す。

【概念図の読み方】
上に 4 つの問いをカラム見出しに、左に 2 つの Service ラベルを縦バンドに、右に Tech 結論カラムを配置した行列。各セルが phase ごとに埋まり、Q2 で分岐 (★) が visible、最後に右端の Tech カラムが verdict として光る。

【各 phase の物語】
phase 0 — 空のテンプレート: 4 問 × 2 サービスの行列だけ visible。「同じ問いを 2 サービスに当てはめる」という構造を予告。
phase 1 — Q1 何を守る?: SMBC は「クライアント口座情報 + DeFi 取引履歴」、結婚マッチングは「各ユーザのプロフィール」。どちらも「保護対象」は明確に違うデータ。
phase 2 — Q2 誰が計算?: SMBC は「SMBC オフチェーンサーバ = 単一組織」、結婚は「全参加者 = 複数当事者の入力統合」。ここが ZK / MPC の分岐点。spotlight でハイライト。
phase 3 — Q3 / Q4 残り: SMBC は「リアルタイム + 監査時後追い」「規制当局 + クライアント」。結婚は「リアルタイム」「ユーザ自身」。
phase 4 — 結論: SMBC → ZK proof of compliance + ZK audit trail (単一組織が計算、後で第三者が検証 → ZK)。結婚 → MPC で相互マッチング (複数当事者の入力統合 → MPC)。FHE はどちらにも該当しない (片方は ZK で十分、片方は MPC が最適、FHE は計算オーバヘッドが現時点で過大)。

【講義での強調点】
- 同じテンプレート、違う結論。問いの設計が技術選択を駆動する。
- Q2「誰が計算?」が支配的な分岐: 単一組織なら ZK、複数当事者なら MPC が第一候補。
- なぜ FHE でないか: ① 計算オーバヘッドが現時点では数桁高い、② ZK/MPC で済む problem には適用しない (overkill)。FHE が威力を発揮するのは「クラウドに encrypted data を預けて任意の関数を実行したい」場面 (e.g. FHE-LLM)。
- なぜ ZK でなく MPC でないか (結婚): ZK は「片方向 prove」が前提 — 「私のプロフィールはこれ」と各人が prove しても、相互マッチングの照合は ZK だけでは閉じない。MPC は「複数当事者の秘密入力で関数を協力計算」が本質、相互マッチングの定義そのもの。
- Track C 課題: 各受講者が自分のプロジェクトテーマで同じ 4 問テンプレを埋める。Notion ページに配布済。
