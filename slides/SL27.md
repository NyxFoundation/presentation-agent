Speaker Notes:

【概要】
ZK service 開発で踏みがちな 3 つの罠を、開発パイプライン (仕様 → 制約系/証明系 → 回路設計 → Prove → Verify) の上で順に露出させる。罠 #1 は設計時の取り返しのつかない選択、#2 と #3 は安全性の独立した 2 軸が壊れる典型例。最後の phase で 3 罠が全て認識・修正された secure な ZK service を示す。

【図の読み方】
上段: 5-stage の ZK service pipeline。各 stage が phase ごとに「⚠ 罠が露出」「✓ 修正済」へと morph。最右の Verify stage の状態 (✓/⚠/✗) が罠の波及効果を表す。下段: phase ごとに「TRAP / FIX」2 列で罠の本質と監査時の必須チェックを表示。

【各 phase の物語】
phase 0 — clean pipeline: 5 stage 全部 green ✓、Verify も secure。「これから 3 罠を見ていく」予告。
phase 1 — 罠 #1 [設計]: stage ② (制約系 / 証明系) が amber に。R1CS / Plonkish / AIR / CCS の制約系と Groth16 / PLONK / Halo2 / Jolt / SP1 / Longfellow の証明系は後から変えられない、検証コスト・対応言語・prover メモリが桁違い。例: Jolt は prover RAM 要求が大きいので mobile / IoT には不向き。Verify は ⚠ setup risk (後で破綻するわけではないが、コスト・拡張性の制約が後から効いてくる)。
phase 2 — 罠 #2 [安全性]: stage ③ (回路設計) が red に。soundness ≠ zero-knowledge — 「証明できる」と「秘密が漏れない」は独立、両方とも独立に壊れうる。実例: Semaphore signal hash bug — public input "signalHash" が回路内で実際に使われていなかったため、attacker は valid proof を取得後に signalHash だけ書き換えて任意 signal を偽装できた。修正は signalHashSquared = signalHash² という非線形制約を追加。Verify は ✗ BROKEN。
phase 3 — 罠 #3 [安全性]: stage ④ (Prove + Fiat-Shamir transcript) が red に。Fiat-Shamir の RO instantiation を雑に扱うと突破される。KRS25 (Khovratovich-Rothblum-Soukhanov, eprint 2025/611) が GKR-based SNARK の現実的攻撃を提示。Sumcheck / Jolt のハッシュ選択と transcript design は監査必須項目。「論文は安全」と「実装は安全」の差。Verify は ✗ BROKEN。
phase 4 — 3 罠回避: stage ②③④ すべて ✓ checkmark で fixed。下段に監査時の 3 チェック項目 (制約系/証明系を先に固定 / public input が回路内で制約される / Fiat-Shamir RO の instantiation 検証) が並ぶ。Verify ✓ secure。

【講義での強調点】
- 罠 #1 は「失敗ではなくロックイン」: 監査で気付いても作り直しコストが膨大。最初に決める。
- 罠 #2 は soundness と ZK の二軸を別個に保証する必要 → unit test に「public input swap 攻撃が通らないこと」を加える。
- 罠 #3 は実装層の罠: 論文の RO assumption が現実の hash で realize されない場合がある。Algebraic RO 系の instantiation を選ぶか、KRS25 のような既知攻撃に対する明示的なレビューを通す。
- 5 罠だけ深掘りし、残り 8 罠はカード配布 (Track C 課題に紐付け)。
- これら 3 罠は全て「コードを書く前 / 監査チェックリスト」で検出可能 — Week 6 のセキュリティレビュー演習の伏線。
